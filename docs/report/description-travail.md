# Description du travail à réaliser

## Choix techniques et implémentation

Pour réaliser le site UTSEUS, nous avons retenu Astro comme framework principal, plutôt qu'une approche traditionnelle en HTML, CSS et JavaScript écrits à la main. Astro est un outil récent, pensé pour générer des sites essentiellement statiques : on écrit des composants réutilisables, on déclare du contenu sous forme de fichiers, et l'outil produit un dossier de pages HTML prêtes à servir, avec très peu de JavaScript embarqué. Ce positionnement collait à plusieurs contraintes du projet.

Premier point, il s'agit d'un projet de cours, livré par une équipe de trois personnes en six semaines, avec un objectif de site institutionnel. Le besoin n'est pas une application interactive complexe, mais un site éditorial multilingue, esthétique et accessible, qui présente l'UTSEUS, ses programmes et ses projets. Astro correspond exactement à ce profil : il prend en charge l'internationalisation, les composants visuels et l'intégration de contenu rédactionnel riche, sans imposer la lourdeur d'un framework d'application comme React ou Vue.

Deuxième point, la cible de déploiement est un hébergement statique fourni par l'UTC, c'est-à-dire un serveur Apache classique accessible par SFTP. Nous n'avons aucun serveur applicatif, aucune base de données, aucun runtime disponible en production. Il faut produire un dossier de fichiers HTML, CSS et images, à téléverser tel quel. Astro produit exactement ce livrable. Un framework comme Next.js ou Nuxt, qui suppose la présence d'un serveur Node, aurait été incompatible avec cette contrainte. Astro la respecte sans aménagement.

Reste la question évidente : pourquoi ne pas écrire le site directement en HTML, CSS et JavaScript classiques, sans aucun framework ? C'est une option défendable pour un site de quelques pages, et elle aurait été plus accessible à un débutant qui découvre le développement web. L'avantage est immédiat : pas de chaîne de compilation, pas de dépendances à installer, pas de vocabulaire spécifique à apprendre. On ouvre un éditeur, on écrit une balise, on rafraîchit le navigateur, et le résultat est là.

Le problème apparaît dès qu'on multiplie les pages et les langues. Notre site comporte une page longue déclinée en trois langues (français, anglais, chinois), donc trois versions à maintenir en parallèle. Le menu, l'en-tête, le pied de page et chaque carte de projet doivent rester strictement identiques d'une langue à l'autre, sauf pour le texte traduit. En HTML pur, cela revient à copier-coller le même balisage des dizaines de fois et à corriger chaque coquille à plusieurs endroits. Une simple modification du menu se transforme en chasse aux occurrences. Astro permet d'écrire un composant une seule fois, de le réutiliser partout, et de séparer proprement la structure et le contenu traduit. Sur ce périmètre, le gain de fiabilité dépasse largement le coût d'apprentissage.

Pour quelqu'un qui n'est pas familier avec le développement moderne, Astro reste cependant plus exigeant qu'un fichier HTML brut. Il faut installer Node, lancer une commande de build, comprendre que les fichiers du framework ressemblent à du HTML mais acceptent des morceaux de logique. La courbe d'apprentissage est réelle, même si Astro est volontairement plus simple que React ou Vue. En contrepartie, un contributeur qui rédige du contenu ne touche jamais au code des composants : il édite uniquement des fichiers de texte avec des règles de structure documentées. Cette séparation entre rôles techniques et rôles rédactionnels est l'un des bénéfices les plus concrets du choix d'Astro pour une équipe mixte comme la nôtre.

L'autre avantage important d'Astro tient à la performance et à l'accessibilité. Comme le site est servi en HTML pré-généré, sans JavaScript inutile, les pages se chargent vite, sont lisibles par les lecteurs d'écran, et passent les audits standards sans bricolage particulier. Un site en HTML, CSS et JavaScript écrit à la main peut atteindre les mêmes résultats, mais il est plus facile d'y introduire des erreurs d'accessibilité sans s'en rendre compte. Avec Astro, beaucoup de bonnes pratiques sont implicites dès qu'on suit la structure proposée.

L'inconvénient principal, dans notre contexte, tient à la dépendance à un outil tiers relativement jeune. Astro évolue vite, ses conventions changent d'une version majeure à l'autre, et sa documentation suppose une certaine familiarité avec l'écosystème JavaScript. Pour un projet de cours, ce risque reste limité, parce que la version livrée est figée et que le site continuera à fonctionner même si le framework évolue ensuite. Mais pour une maintenance à long terme par une équipe différente, le transfert de compétences serait plus exigeant qu'avec un site en HTML pur. C'est un arbitrage à assumer.

Pour la mise en forme visuelle, nous nous appuyons sur Tailwind CSS, utilisé conjointement avec Astro. C'est un outil qui permet d'écrire les styles directement à proximité des balises, sans gérer une bibliothèque de classes nommées séparément. Le choix s'inscrit dans la même logique que celui d'Astro : éviter le code dupliqué et garder la cohérence visuelle facile à maintenir. Pour un débutant, Tailwind a lui aussi un coût d'apprentissage initial, car il faut s'approprier son vocabulaire de classes ; mais une fois ce vocabulaire assimilé, il accélère l'itération visuelle de manière sensible.

## Processus de conception

Le projet a suivi un déroulement en étapes conceptuelles claires, plutôt qu'un développement linéaire des pages les unes après les autres. Cet ordre a structuré la manière dont l'équipe a travaillé.

La première étape a consisté à mettre en place le squelette technique avec Astro. Avant toute discussion sur le contenu ou les couleurs, il fallait que le site existe en tant que système cohérent : une page qui s'affiche, un mécanisme pour ajouter des sections, une gestion des trois langues, une chaîne de build qui produit un dossier déployable. Cette étape est invisible pour un lecteur du site final, mais elle conditionne tout le reste. Tant qu'elle n'est pas stabilisée, le contenu écrit risque de se perdre à la prochaine refonte de structure. Nous avons donc commencé par poser ce socle, en utilisant du texte provisoire à la place du contenu réel et en remplissant les sections avec des données factices.

La deuxième étape a porté sur l'identité visuelle, c'est-à-dire le choix des couleurs, de la typographie et du registre graphique général. Cette étape a été menée en parallèle des premières maquettes, et a abouti à une direction éditoriale assumée : une palette resserrée, des typographies marquées, des mises en page qui assument un contraste fort entre les sections. Le rôle du framework, ici, est de permettre que ce choix visuel se concrétise sans réécrire le code : nous changeons les valeurs de couleurs et de polices à un seul endroit, et toutes les pages se mettent à jour automatiquement. Sans cette indirection, chaque ajustement de charte aurait demandé une revue complète du site.

La troisième étape est celle de la rédaction et de la curation du contenu réel : textes de présentation, descriptions de projets, témoignages d'étudiants, photos. Une fois la structure stable et la charte visuelle posée, le travail rédactionnel pouvait avancer sans craindre que le cadre change sous ses pieds. C'est aussi l'étape qui implique le plus fortement les membres de l'équipe non développeurs, qui éditent directement les fichiers de contenu sans avoir à intervenir sur le code. Cette autonomie a fluidifié la collaboration, parce qu'elle a évité d'engorger une seule personne sur tous les changements de texte.

La quatrième et dernière étape regroupe le polissage : détails d'interaction, transitions discrètes, icônes, vérification systématique de l'accessibilité, audit des liens externes, et enfin le déploiement sur l'infrastructure cible. C'est l'étape la moins visible de l'extérieur, mais la plus chronophage, parce que la qualité d'un site institutionnel se juge autant sur ses détails que sur sa structure d'ensemble. Le travail y consiste à reprendre chaque section pour traquer les irrégularités, les contrastes insuffisants, les comportements inattendus au clavier, plutôt qu'à ajouter de la matière nouvelle.

Ce découpage en quatre temps (cadre, identité, contenu, finition) n'est pas spécifique à Astro, mais le framework le rend praticable sans douleur. Chaque étape peut être menée sans craindre que la suivante remette en cause le travail déjà fait, parce que les responsabilités sont clairement séparées dans le code lui-même : le cadre vit dans les composants, l'identité dans les variables de style, le contenu dans les fichiers de texte, la finition dans des ajustements transversaux. Pour un projet réalisé par une petite équipe dans un temps court, c'est cette séparation qui nous a permis d'avancer en parallèle sans collisions.
